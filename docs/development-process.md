# Процесс разработки

Этот документ описывает рекомендуемый цикл облачной разработки через ChatGPT.com + GitHub.

## 1. Инициирование работы

Новая функция начинается с Issue. Issue должен отвечать на три вопроса:

- какую проблему решаем;
- для кого она важна;
- как поймём, что задача выполнена.

Для бага указываются воспроизводимость, фактическое и ожидаемое поведение.

## 2. Спецификация

Для функциональности создаётся каталог `specs/<NNN>-<slug>/` на основе `specs/_template/`.

Минимальный набор:

- `spec.md` — что и зачем строим;
- `plan.md` — как строим;
- `tasks.md` — конкретные шаги реализации.

### `spec.md`

Содержит:

- контекст и проблему;
- цели;
- что не входит в scope;
- пользовательские сценарии;
- функциональные требования;
- нефункциональные требования;
- критерии приёмки;
- открытые вопросы.

Технические детали здесь минимальны.

### `plan.md`

Содержит:

- выбранную архитектуру;
- затрагиваемые модули;
- изменения данных/API;
- стратегию тестирования;
- риски и миграции;
- при необходимости ADR.

### `tasks.md`

Задачи должны быть достаточно малы, чтобы результат каждой можно было проверить.

## 3. Проверка согласованности

До реализации нужно проверить:

- покрывает ли plan все требования spec;
- есть ли task для каждого существенного пункта plan;
- нет ли задач, не объяснённых spec/plan;
- определён ли способ проверки критериев приёмки.

## 4. Реализация

Рекомендуемая модель веток:

- `feat/<issue>-<slug>`;
- `fix/<issue>-<slug>`;
- `chore/<issue>-<slug>`.

Код меняется небольшими шагами. После значимых изменений запускается `bash scripts/ci`.

## 5. Pull Request

PR должен ссылаться на Issue и spec и содержать:

- что изменено;
- почему выбран такой подход;
- как проверить;
- какие риски/ограничения остались.

Если в ходе реализации потребовалось отойти от plan, сначала обновляется plan/ADR, затем код.

## 6. CI

### Быстрый CI

Запускается на push и PR. Его задача — быстро ловить типовые ошибки.

Контракт: `bash scripts/ci`.

### Полный CI

Используется для интеграционных/e2e/миграционных и других тяжёлых проверок.

Контракт: `bash scripts/ci-full`.

Полный CI также можно запускать вручную через GitHub Actions.

## 7. Диагностика ошибок

При падении workflow агент должен сначала изучить:

1. упавший job;
2. конкретный step;
3. полный log;
4. диагностический artifact;
5. только после этого менять код.

`scripts/diagnostics` собирает безопасный текстовый пакет с контекстом выполнения. Конкретный проект может расширить его через `scripts/project-diagnostics`.

## 8. Converge перед merge

Перед завершением PR нужно заново сравнить реализацию со spec/plan/tasks:

- все ли критерии приёмки выполнены;
- не появился ли незапланированный scope;
- все ли задачи актуально отмечены;
- не устарели ли docs/ADR;
- проходит ли CI.

Если обнаружены расхождения, они превращаются в новые tasks либо явно выносятся в отдельный Issue.

## 9. Merge

По умолчанию рекомендуется squash merge после зелёного обязательного CI.

`main` должен оставаться рабочим состоянием проекта.

## 10. GitHub Spec Kit

Шаблон совместим по модели с GitHub Spec Kit, но не зависит от него.

Если Spec Kit подключён, рекомендуется сопоставление:

- constitution → `docs/constitution.md`;
- specify → `spec.md`;
- plan → `plan.md`;
- tasks → `tasks.md`;
- implement → рабочая ветка;
- converge → финальная сверка перед merge.

Это позволяет использовать официальный CLI/skills без необходимости форкать его файлы в этом template repository.

## 11. GitHub Pages

Pages не нужен для разработки приложения и поэтому не включён в обязательный pipeline. Если проекту нужна публичная документация, можно добавить отдельный manual workflow публикации `docs/` через GitHub Pages.

Hosting самого приложения, preview environments, staging и production относятся к отдельному слою инфраструктуры и не входят в этот шаблон.
